# نظام مستندسازی — پلتفرم عملیاتی سازمانی ideaone

> این سند نقشه کامل مستندات پروژه است. هر سند یک «نوع» و یک «قانون نگهداشت» دارد.
> آخرین بازنگری: ۱۴۰۵/۰۶/۱۷ (افزوده: CMD-012 خط پایهٔ عمومی + دروازهٔ شاخهٔ main) · نگهدارنده: تیم پلتفرم

## اصول نظام مستندسازی

1. **مستند از کد جلوتر است** — هیچ فرم، نما یا API بدون SPEC مصوب ساخته نمی‌شود؛ SPEC منبع حقیقت طراحی است.
2. **هر تغییر رفتاری = به‌روزرسانی سند در همان PR** — سندی که با کد ناهم‌خوان شود معیوب‌تر از نبود سند است.
3. **هر سند یک مالک و یک وضعیت دارد** (`پیش‌نویس | فعال | منسوخ`) — سند بی‌وضعیت حذف می‌شود.
4. **جزئیات در سند، خلاصه در کد** — سطح جزئیات SPEC طوری است که یک توسعه‌دهنده تازه‌وارد بتواند فرم را «فیلد‌به‌فیلد» بسازد.
5. **نام‌گذاری فایل‌ها ثابت است** — تغییر نام سند = شکستن ارجاع‌های کد (کامنت‌های `service.ts` به سناریوها ارجاع می‌دهند).

> ۳۴ ردیف رجیستری SPEC ندارند (۲۶ مصوبِ INACTIVE ردیف‌دار + ۶ چشم‌انداز + ۲ انتظار-ادغام — کل رجیستری: ۴۱ ردیف طبق CMD-011): پیش از شروع پیاده‌سازی هرکدام، SPEC با قالب واحد نوشته می‌شود (قاعده «مستند از کد جلوتر»).

هر SPEC شامل: هدف/دامنه → ماتریس مجوز نقش‌ها → مدل داده → **نماها (ستون‌به‌ستون)** → **فرم‌ها (فیلد‌به‌فیلد با اعتبارسنجی)** → گردشکار/ماشین حالت → API (ورودی/خروجی/خطا) → اعلان‌ها و رویدادها → حالت‌های خالی/خطا/موبایل → شکاف‌های v1 و الزامات v2 (با ارجاع به وظیفه نقشه راه).

| رویداد | اقدام الزامی |
|---|---|

| تغییر رجیستری پلاگین‌ها (layer/domain/فاز/منو) | به‌روزرسانی ADR-008 و جدول رجیستری `architecture/06-module-registry.md` |
| افزودن/بازنام‌گذاری ماژول یا ورود به فاز جدید | به‌روزرسانی ماتریس `product/04-module-coverage.md` در همان PR + اجرای `validate-modules.mjs` (برای تغییر رجیستری: ثبت CMD در `decisions/`) |
| تصمیم معماری جدید | ADR جدید (شماره بعدی) |
| ورود به فاز جدید نقشه راه | به‌روزرسانی وضعیت وظایف در فایل فاز |
| پایان هر تسک عامل | ثبت در `worklog.md` (ریشه مخزن) |
