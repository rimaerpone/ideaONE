# ADR-004 — اعلان بلادرنگ با بلیت HMAC و تحویل at-least-once

- وضعیت: پذیرفته‌شده (پیاده‌سازی‌شده در Task 2-rt)
- تاریخ: ۱۴۰۵/۰۶/۰۵

## زمینه

اعلان‌ها ابتدا polling ۳۰ ثانیه‌ای بودند (تأخیر پذیرش پایلوت). ارتقا به WebSocket مستلزم رفع دو مسئله سندباکسی بود: فوروارد تک‌پورت گیت‌وی Caddy و احراز هویت سوکت بدون افشای session cookie.

## تصمیم

۱. **مینی‌سرویس Bun مستقل** `mini-services/realtime` — socket.io روی پورت ۳۰۰۳ با path `/` (قاعده Caddy). API داخلی تزریق رویداد روی `127.0.0.1:3004` با هدر `x-internal-key` (کلید اشتراکی، مقایسه timingSafeEqual) — **چون socket.io با path '/' کل HTTP سرور خودش را تصاحب می‌کند**.
۲. **ثبت‌نام امن با بلیت:** کلاینت `GET /api/realtime/ticket` (مبتنی بر نشست httpOnly) → بلیت `<exp>.<HMAC-SHA256(userId:exp)>` با عمر ۶۰ ثانیه → سرور سوکت با HMAC خودش راستی‌آزمایی و join به اتاق `user:<userId>` — شنود متقابل غیرممکن است.
۳. **قیف واحد `notify()`:** ثبت در دیتابیس (منبع حقیقت) + `pushRealtime()` فایر-اند-فورگت با timeout 2.5s و سکوت عمدی در خطا.
۴. **تحویل at-least-once:** polling ۳۰ ثانیه‌ای به‌عنوان پوشش قطعی سوکت باقی است؛ کلاینت با `rtVersion` در zustand هر دو مسیر را idempotent مصرف می‌کند.
۵. اتصال مجدد خودکار socket.io (reconnection) + نمایش وضعیت («بلادرنگ/آفلاین») در UI.

## پیامدها

✅ تأخیر اعلان از ≤۳۰s به ~۱۵۰ms · امنیت بدون تغییر مدل نشست · قطعی سرویس push هیچ درخواست API را نمی‌شکند
❌ سرویس اضافه برای راه‌اندازی پس از ری‌بوت (runbook RB-01) · کلید اشتراکی باید در استقرار واقعی از env بیاید

## شواهد E2E
