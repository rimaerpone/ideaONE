# ADR-010 — پروتکل اجرای نشست (قانون روش کار عامل‌ها)

- وضعیت: پذیرفته‌شده (فرمان صریح کارفرما — «این مواردی که من گفتم را بررسی کن، بهینه کن و تبدیل به قانون کن»)
- تاریخ: ۱۴۰۵/۰۶/۱۶ (۲۰۲۶-۰۹-۰۲)
- مرتبط: `AGENTS.md` (بخش «محیط سندباکس» — متن الزامی اجرا) · `worklog.md` (حافظه نشست‌ها) · ADR-005 (قواعد بقا) · ADR-006 (نظام مستندسازی) · نقشه راه واحد ۱۸گامی/۶موجی (P0.5)

## زمینه و انگیزه

مسیر پیشِ رو طولانی و پیچیده است: ۶ موج، ۳۲۴ وظیفه، صف بازسازی R9..R17 و ۵ حکم باز کارفرما. تجربه ثبت‌شده در worklog نشان می‌دهد سه ریسکِ روش (نه فناوری) تهدید اصلی پیوستگی‌اند:

1. **گم‌شدن دانش چت‌محور:** گزارش «نقشه راه واحد» (unified-roadmap-2026-09-01) فقط در چت تحویل شد و ثبت worklog آن جلسه به‌سبب سه خطای متوالی ابزار از دست رفت — بازیابی فقط با بازسازی دستی در نشست بعد ممکن شد.
2. **قطعی محیط سندباکس:** دو رخداد برگشت محیط (یک روز کار حذف شد — رخداد ۰۶/۰۹) و خطاهای ابزار در لحظه‌های حساس.
3. **زمینهٔ محدود نشست:** فایل‌های حیاتی بزرگند (worklog ~۱۸۰KB، AGENTS.md ~۵۵KB) و هر نشست با خواندن کاملِ آن‌ها صرف نمی‌شود.

کارفرما برای همین ریسک‌ها روش زیر را خواست و مقرر شد **بهینه و به قانون تبدیل شود**.

## تصمیم

هر نشستِ کار (عامل AI یا انسانی) از پنج مرحلهٔ الزامی عبور می‌کند. متن اجرایی قانون در `AGENTS.md` (بخش «پروتکل اجرای نشست») است — اینجا فقط صورت مسئله و پیامد ثبت می‌شود.

| مرحله | نام | شرط عبور |
|---|---|---|
| ۱ | **بررسی** | ممیزی شروع نشست (طبق جدول ماندگاری AGENTS.md) + تعیین «وظیفه بعدی صف» از آخرین ورودی worklog — بدون این، هیچ تغییری نوشته نمی‌شود |
| ۲ | **بیانیه** | فهرست وظایف شماره‌دار **پیش از اجرا**؛ هر وظیفه = دلیل + خروجی + معیار پذیرش — کارِ بیانیه‌نشده ممنوع |
| ۳ | **اجرا** | بسته‌های کوچک (S/M) + تأیید فوریِ هر وظیفه + خردکردن وظیفه بزرگ در همان نقطه |
| ۴ | **تثبیت** | مستندات وضعیت‌دار هم‌کامیت با کد + `bun run check` سبز + کامیت + ورودی worklog (قالب موجود) |
| ۵ | **پیشنهاد** | ۲ تا ۳ گام بعدی با دلیل + فهرست صریح حکم‌های باز کارفرما |

### قوانین تاب‌آوری سندباکس (بهینه‌شده از نگرانی‌های کارفرما)

| قانون | متن | ریشهٔ رخداد |
|---|---|---|
| **چت سند نیست** | هر گزارش/تصمیم/حکم مهم باید در همان نشست به مستند دائمی (docs/ یا worklog) تبدیل شود؛ تصمیمِ فقط-در-چت = از‌دست‌رفته | unified-roadmap-2026-09-01 |
| **دو شکست ابزار** | پس از دو شکست متوالیِ همان ابزار: توقف، ثبت در worklog، اطلاع به کارفرما — تلاش سومِ کور ممنوع | سه خطای متوالی ثبت worklog |
| **بسته کوچک** | هر نشست حداکثر ۳-۵ وظیفهٔ قابل‌تکمیل؛ کار نیم‌تمام بدتر از کار شروع‌نشده است — اگر نشست باید نصف شود، «وضعیت ادامه» در worklog ثبت می‌شود | زمینهٔ محدود نشست |
| **بودجهٔ زمینه** | خواندن هدفمند (tail/grep/بازه) به‌جای بازخوانی کل فایل‌های بزرگ؛ وظایف طوری خرد شوند که زمینهٔ نشست کافی باشد | worklog/AGENTS حجیم |
| **ایستگاه میانی** | هیچ بستهٔ سبزِ بی‌کامیت رها نشود (قاعدهٔ موجود AGENTS.md — اینجا تثبیت می‌شود) | رخداد حذف یک روز کار |
| **وضعیت صادقانه** | هر ادعای «انجام‌شده» باید شاهد داشته باشد (تست سبز / کامیت / فایل خروجی) — ادعای بدون شاهد ممنوع | ممیزی‌های متوالی گزارش‌محور |

## گزینه‌های رد‌شده

- **ادامهٔ روش سابق (شروع مستقیم کار):** ساده‌تر در کوتاه‌مدت، اما همان مسیری که به سه رخداد بالا انجامید.
- **ثبت قانون فقط در docs (بدون AGENTS.md):** عامل‌ها AGENTS.md را می‌خوانند نه همهٔ docs — قانون ناخوانده اجرا نمی‌شود.
- **ورودی worklog بعد از هر تک-وظیفه (نه پایان بسته):** هزینهٔ ابزار/زمینه بالا؛ راه میانه: کامیت بسته + ثبت کارهای بسته در یک ورودی.

## پیامدها

✅ هر نشست یک «واحد قابل‌حساب» می‌شود: بررسی‌شده، بیانیه‌شده، تأییدشده، تثبیت‌شده — بازیابی پس از هر قطعی حداکثر یک بسته است · ✅ دانش فقط در چت نمی‌ماند · ✅ صف کار (R/P) همیشه از worklog قابل بازسازی است
❌ سربار ثابت هر نشست (~۵-۱۰ دقیقه بررسی و بیانیه) · ❌ وظیفه‌های بزرگ باید از قبل خرد شوند — این خودش انضباط مثبتی است · قانونِ «دو شکست ابزار» گاهی یعنی ادامهٔ کار در نشست بعد (پذیرفته‌شده: هزینهٔ بازیابی از دست‌رفته کمتر از تلاش کور است)
