## ۱. تصمیم

رجیستری سندباکس از وضعیت فعلی (**۲۹ ردیف** با شناسه‌های قدیمی سندباکس) به وضعیت هم‌راستا (**۴۱ ردیف**) بازسازی می‌شود: هر Plugin ID مصوبِ ردیف‌دار، دقیقاً با شناسهٔ v1.1 ثبت می‌شود؛ ردیف‌های زیرساخت هسته خارج از ۳۳ ابقا می‌شوند؛ ردیف‌های چشم‌اندازی با نشان صریح نگه داشته می‌شوند.

## ۳. ماژول‌های مصوب بدون ردیف مستقل (۵ ردیف — عمداً)

| Plugin ID مصوب | پوشش | دلیل نبودِ ردیف |
|---|---|---|
| `users` | منوی «کاربران» + سرویس نشست/هویت داخل پلتفرم (۱۴ کاربر زنده) | پیاده‌سازی کامل داخل `settings`/کد پلتفرم؛ ردیف جدا = دوباره‌کاری تا زمان استخراج پلاگین در موج بعدی |

| `notification-center` | Notification + بلادرنگ + ScheduledJob | همان |

## ۴. حساب نهایی

```
۵  زیرساخت هسته (بستر)          → خارج از ۳۳
۲۸ ردیف مصوبِ ردیف‌دار           → ۳۳ − ۵ پوشش پلتفرمی = ۲۸ ✓
۶  چشم‌انداز + ۲ انتظار ادغام    → خارج از ۳۳ با نشان صریح
─────────────────────────────────
۴۱ ردیف رجیستری نهایی
```

## ۵. اعمال و راستی‌آزمایی

| گام | شاهد |
|---|---|
| بازسازی `scripts/seed.ts` (modDefs + انبارهای سه‌گانه + dependsOnها) | seed قابل اجرا + idempotent (حذف/بازسازی) |
| `bun scripts/validate-modules.mjs` | **۳۳/۳۳ PASS** (پارس فهرست از module-list.md + انطباق با رجیستری زندهٔ Neon) |
| رگرسیون | `bun run check` سبز · باتری انبار/کدینگ سبز |
| سایدبار | شمار پلاگین‌ها از رجیستری زنده (نه متن ثابت) |

## ۶. ریسک‌ها و تصمیم‌های جانبی

- **بازنام‌گذاری ردیف‌های هرگز-منتشرنشده:** مجاز و ارزان طبق فایل فاز (§۳) — کد `src/` به هیچ code قدیمی (finance/commercial/production/…) ارجاع ندارد (جست‌وجوی سراسری پیش از اعمال انجام شد).
- **تفکیک commercial:** وابستگی `partners, products, warehouse` به `sales-orders` و `partners, products` به `purchase-orders` نگاشت شد.
- **ماده ۱۶۹ / مؤدیان:** `tax-management` و `integration-moadian` دو ردیف جدا می‌مانند (دامنهٔ مستقل طبق v1.1) اما هر دو INACTIVE تا P8/P10.
- **`purchase-vendors`:** با CMD اصلاحی آینده (پس از P4) ممکن است ردیف مستقل بگیرد اگر دامنهٔ قرارداد/ارزیابی از شرکا جدا شود.
