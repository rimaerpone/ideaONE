## ۱. چرا این ممیزی؟

P1.5 (پوسته چندسندی) و گذر «بررسی عمیق فرم‌ها» (۶۷ بهبود) استاندارد پایه را ساختند: تب کاری، فرم صفحه‌ای، حذف دیالوگ اطلاعاتی، نوار وضعیت چرخه عمر. اما استاندارد «پایه» با استاندارد «ERP تولیدی که کاربر ۸ ساعت روز با آن کار می‌کند» فرق دارد. این سند با ممیزی الگوهای ۵ مرجع جهانی و دست‌کم ۵ بازیگر ایرانی، شکاف‌های باقی‌مانده را اولویت‌بندی می‌کند و مبنای بازنویسی نقشه راه UX است.

**اصل راهنما (از بازخورد کاربر):** ذات ERP «تراکم اطلاعات» است — کاربر عملیاتی همزمان چند رکورد باز دارد، در فرم‌ها ده‌ها فیلد و جدول اقلام می‌بیند و بین نماها جابه‌جا می‌شود. پس هر تصمیم چیدمان باید با سنجه «اطلاعات بیشتر در صفحه، با نظم بیشتر» سنجیده شود، نه «سادگی بصری به بهای اتلاف فضای مانیتور».

## ۲. الگوهای استخراجی از مراجع جهانی

### ۲.۱ SAP Fiori — چیدمان ستونی انعطاف‌پذیر (Flexible Column Layout)
- **الگو:** یک صفحه هم‌زمان ۱ تا ۳ ستون: فهرست + رکورد + جزئیات؛ ستون‌ها قابل تغییر عرض/جمع‌شدن‌اند؛ ناوبری «از فهرست به رکورد» بدون ترک صفحه (منبع: s1 — SAPUI5 Flexible Column Layout Tutorial).
- **درس برای ما:** پیمایش سریع ده‌ها رکورد پشت‌سرهم در «تبِ هر رکورد» سنگین است؛ نمای فهرست به یک «پیش‌نمایش» کنار فهرست نیاز دارد.
- **الگوی مکمل Fiori Elements:** Smart Table با «واریانت‌های ذخیره‌شده» (نماهای شخصی ستون‌ها/فیلترها per کاربر) — ما فقط show/hide ستون داریم، بدون ذخیره.

### ۲.۲ Microsoft Dynamics 365 (UCI) — فرم = تب ← ستون ← سکشن ← فیلد
- **الگو:** مدل ذهنی طراح فرم D365: فرم از «تب‌ها» تشکیل شده، هر تب از ۱–۴ «ستون»، هر ستون از «سکشن‌های عنوان‌دار» و هر سکشن از فیلدها (منبع: s2 — UCI Form Design Guide + Appearance of main forms). سکشن‌ها با «برچسب گروه» مرتب می‌شوند نه با خطوط.
- **درس برای ما:** فرم‌های ما ۲–۳ ستونه‌اند اما **بدون سکشن‌بندی عنوان‌دار** — در فرم‌های متراکم آینده (مالی/تولید) بدون سکشن، فیلدها «دیده نمی‌شوند». همچنین D365 «هدر فرم با فیلدهای کلیدی همیشه‌مرئی» دارد — شناسنامه InfoGrid ما معادلش است.
- **الگوی Reference Panel:** تب پایین فرم برای رکوردهای مرتبط (مثل اقلام مرتبط/اسناد مرتبط) — پیش‌نیاز معماری داده در فازهای بعد.

### ۲.۳ Odoo — سوییچر نما + Favorites/Chatter
- **الگو:** پنجره اقدام هر مدل چند «نما» دارد: List / **Kanban** / Calendar / Graph / Form؛ منوی «Filters/Favorites» فیلترهای ذخیره‌شده per کاربر می‌سازد؛ **Chatter** (گفتگو+فعالیت+پیوست) در همه فرم‌ها سمت چپ/راست است (منبع: s3 + research/odoo-*.json).
- **درس برای ما:** «گردش نامه» فقط برای نامه هست؛ سایر رکوردها (سند انبار، درخواست) تاریخچه اقدام ندارند. Chatter/Odoo-style «خط زمان اقدامات رکورد» الگوی مرجع است. Kanban برای نامه‌ها/درخواست‌ها ارزشمند اما پس از تراکم فرم و گرید.

### ۲.۴ Salesforce Lightning — Console + Split View + List Views
- **الگو:** اپ Console = پوسته تب‌محور (ما داریم) + **Split View** (ستون باریک فهرست کنار رکورد) + List Views ذخیره‌شده/سنجاق‌شده + **Path** (نوار وضعیت گام‌ها — ما داریم) + Utility Bar (پنل پایین برای تاریخچه/یادداشت سریع).
- **درس برای ما:** Split View تأیید دوم بر نیاز «پیش‌نمایش کنار فهرست» است؛ List Views شخصی = همان شکاف Fiori variants.

### ۲.۵ بهترین‌های گرید داده سازمانی ۲۰۲۴–۲۰۲۶ (منبع: s6)
- **انتخاب گروهی + نوار اقدام گروهی** (Bulk actions) — صرفه‌جویی اصلی زمان کاربر داده‌محور.
- **ویرایش درون‌خطی** سلولی با اعتبارسنجی همان‌جا.
- **نمای ذخیره‌شده** (فیلتر+مرتب‌سازی+ستون‌ها) با سنجاق نمای پیش‌فرض.
- شخصی‌سازی ستون‌ها: نمایش/مخفی/عرض/ترتیب با **persist**.
- فیلتر سریع ستونی؛ حالت تراکم (compact/comfortable)؛ ستون کلیدی فریزشده.

### ۲.۶ رقبای ایرانی
- **راهکاران (همکاران سیستم، وب):** ERP وب‌محور جامع با تاکید روی داشبورد و ماژول‌های یکپارچه (research/rahkaran*.json) — نسل وب، چیدمان داشبورد-محور.
- **تیمیار (وب، ادعای قابل مقایسه با SAP):** ERP تمام‌ایرانی تحت وب (research/teamyar*.json) — معماری وب مدرن با ماژول‌گرایی.
- **نسل دسکتاپ (سپیدار/سایان/تدبیران):** MDI چندپنجره‌ای متراکم، ورود داده کیبورد-محور، جستجوی سریع، جداول درشت (research/iran-erp-compare.json) — درس: **تراکم و سرعت ورود داده** برای کاربر ایرانی آرمان است؛ زیبایی‌گریزی به بهای فاصله‌ کلیک، بد است.
- **نتیجه ترکیبی:** کاربر ایرانی ERP با هر دو جهان سروکار دارد؛ مزیت رقابتی ما = تراکم نسل دسکتاپ + نظم/وب نسل راهکاران/تیمیار.
