# P1.5 — پوسته چندسندی و فرم ERP (UX Shell v2)

وضعیت: **کامل (۱۴/۱۴ — تکمیل با T13 در ۱۴۰۵/۰۶/۱۷)** | مالک: محصول/فرانت‌اند | درج: ۱۴۰۵/۰۶/۱۶ (پاسخ به بازخورد کاربر: «پاپ‌آپ گزینه خوبی برای نمایش اطلاعات نیست · نبود سیستم تب‌محور · سایدبار باید در دسکتاپ هم جمع‌شونده باشد · فرم‌ها باید اطلاعات بالایی داشته باشند»)
پیش‌نیاز: P1-T1/T2/T3/T12/T20/T21/T22/T23 (انجام‌شده) | خروجی گیت: گیت G2 (UX استاندارد)

> چرا این فاز؟ ذات ERP «تراکم اطلاعات» است: کاربر عملیاتی همزمان یک نامه، یک سند انبار و موجودی را باز نگه می‌دارد و بین‌شان جابه‌جا می‌شود. معماری تک‌نمای فعلی (activeView تکی + دیالوگ برای جزئیات) این چرخه کار را نمی‌پذیرد. الگوی مرجع: پوسته چندسندی Axelor/راهکاران/تیمیار + فرم‌های هدر‌دار Odoo.

## ۱. معماری هدف

```
┌─────────┬──────────────────────────────────────────────────┐
│ سایدبار  │ هدر (سوییچر شرکت، اعلان، پروفایل، دکمه جمع‌کردن منو) │
│ ریل/کامل ├──────────────────────────────────────────────────┤
│         │ نوار تب: [داشبورد][نامه‌ها][نامه ۱۲۳ ×][سند ۴۵ ×]   │
│         ├──────────────────────────────────────────────────┤
│         │ برگردد: دبیرخانه / نامه ۱۲۳                        │
│         │ ┌ هدر رکورد: عنوان + نشان‌ها + نوار وضعیت (statusbar)│
│         │ ├ نوار اقدام: [قطعی‌سازی][ابطال] … (چسبان)          │
│         │ ├ شناسنامه: شماره · تاریخ · طرف · انبار · جمع کل    │
│         │ ├ تب‌های داخلی: [محتوا][پیوست‌ها][گردش کار]          │
│         │ └ بدنه                                            │
└─────────┴──────────────────────────────────────────────────┘
```

قواعد ناوراست:
1. **دیالوگ فقط برای تأیید (ConfirmDialog)، انتخاب‌گرها و ویزاردهای کوتاه** — نمایش/ویرایش رکورد همیشه صفحه کامل است.
2. **هر نما یا رکورد = یک تب** با عنوان قابل‌فهم؛ بازِ مجدد همان رکورد، تب موجود را فعال می‌کند (dedup).
3. **فرم ثبت/ویرایش هم صفحه است نه دیالوگ** — با هدر اطلاعاتی (نوع، تاریخ، شماره پیش‌رو، جمع زنده) و پس از ذخیره، همان تب به تبِ رکوردِ ذخیره‌شده «جامه‌ویژه» (materialize) می‌شود.
4. فقط تب فعال mount است (بقیه با TanStack Query کش می‌مانند) — حافظه و ۶۰fps.
5. نوار وضعیت چرخه عمر (ثبت → در جریان → پاسخ/تأیید → بایگانی) از نشان‌های پراکنده جایگزین می‌شود.

## ۴. ریسک‌ها و تصمیم‌ها

- **فقط تب فعال mount**: داده در TanStack Query زنده می‌ماند؛ فرم‌های نیمه‌کاره با خروج از تب state را از دست می‌دهند → پذیرفته (تا P1-T24) چون ثبت فرم‌های اصلی سریع است و زبان مشترک «بازگشت با تب» است.
- **URL عمیق**: محدودیت سندباکس (تنها مسیر `/`) → حالت در sessionStorage؛ مهاجرت آدرس‌پذیر به P10 (خروج از سندباکس).
- **جامه‌ویژه تب جدید→رکورد**: تب «سند جدید» پس از ذخیره با تبِ «سند ۴۵» جایگزین می‌شود تا انباشت تب‌های «جدید» رخ ندهد.
- Radix DirectionProvider (RtlProvider) باید نوار تب را هم بپوشاند (CH-24 / درس RTL).
