# RB-01 — راه‌اندازی و پایش سرویس‌های سندباکس

## سرویس‌ها و وضعیت مطلوب

| سرویس | پورت | نقش | بررسی سلامت |
|---|---|---|---|
| Next.js dev (راه‌انداز یک‌باره محیط — نگهبان ندارد!) | 3000 | اپلیکیشن | `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:3000/` → 200 |
| realtime (سوکت) | 3003 | اعلان بلادرنگ | لاگ `mini-services/realtime/realtime.log` باید `registered user=` داشته باشد |
| realtime (API داخلی) | 3004 | تزریق رویداد — فقط localhost | `curl -s http://127.0.0.1:3004/healthz` → `{"ok":true,...}` |
| گیت‌وی Caddy | 81 | دسترسی کاربر + XTransformPort | صفحه از `:81` باز شود |

## احیای Next.js در صورت خاموشی

⚠️ `.zscripts/dev.sh` محیط فقط «راه‌انداز یک‌باره» است — هیچ نگهبان/خود‌احیایی ندارد. اگر پورت ۳۰۰۰ پاسخ نداد (رویداد واقعی: OOM killer پس از بازکامپایل‌های سنگین):

```bash
ss -tlnp | grep 3000          # اگر خالی بود، سرور مرده است
( cd /home/z/my-project && setsid bun run dev >> /dev/null 2>&1 < /dev/null & )
# صبر تا 200: curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:3000/
```

**نکته تاییدشده در تست تاب‌آوری (P0-T15):** اگر زنجیره dev قدیمی هنوز زنده باشد (پروسه‌های `bun run dev` → `bash … | tee dev.log` → `node …/next dev` → `next-server`)، کشتنِ فقط `next-server` کافی نیست — نمونه جدید با خطای «Unable to acquire lock at .next/dev/lock» می‌میرد. در این حالت:

```bash
ps aux | grep -E "bun run dev|next dev|next-server" | grep -v grep   # کل زنجیره را ببینید
kill -9 <pidهای زنجیره>          # از next-server شروع کنید؛ بعد next dev و bun
rm -f .next/dev/lock             # قفل بی‌صاحب را پاک کنید
# سپس همان فرمان راه‌اندازی بالا
```

نشست‌ها در دیتابیس‌اند — احیا نشست‌ها را باطل نمی‌کند. برای کاهش ریسک OOM: مرورگر تست را بعد از اتمام ببندید و از اجرای هم‌زمان چند نمونه dev پرهیز کنید.

## راه‌اندازی سرویس realtime پس از ری‌بوت سندباکس

⚠️ الگوی double-fork الزامی است — `bun run dev &` ساده بین دستورات کشته می‌شود:

```bash
( cd /home/z/my-project/mini-services/realtime && \
    setsid bun run dev >> realtime.log 2>&1 < /dev/null & )
sleep 2
curl -s http://127.0.0.1:3004/healthz   # باید ok:true بدهد
```

لاگ سرویس داخل خود پوشه سرویس نوشته می‌شود: `mini-services/realtime/realtime.log` (ریشه پاک بماند — 02-folder-structure §1).

## خاموشی/ری‌استارت تمیز

⚠️ `pkill -f "mini-services/realtime"` کار نمی‌کند — cmdline پروسه فقط `bun run dev` است (مسیر در argv نیست).
پروسه را از روی پورت پیدا و با pid بکشید:

```bash
ss -tlnp | grep -E ':(3003|3004)'   # pid را از ستون users بگیرید
kill <pid>; sleep 2
ss -tlnp | grep -E ':(3003|3004)'   # باید خالی باشد (پورت‌ها آزاد)
# سپس همان فرمان راه‌اندازی بالا
```

کلاینت سوکت خودش دوباره وصل می‌شود (اثبات‌شده) — نیازی به رفرش دستی نیست.

## تشخیص عیب

| علامت | علت احتمالی | اقدام |
|---|---|---|
| چیپ «آفلاین» در UI | سرویس 3003 بالا نیست | راه‌اندازی مجدد (بالا)؛ کلاینت خودش وصل می‌شود |
| سوکت وصل ولی اعلان نمی‌رسد | API داخلی 3004 پایین / کلید ناهماهنگ | healthz + تطابق `REALTIME_SECRET` (پیش‌فرض هر دو فایل یکسان‌اند) |
| `Transport unknown` روی 3003 | درخواست HTTP عادی به پورت سوکت | طبیعی است — API داخلی روی 3004 است |
| اعلان با تأخیر ۳۰s می‌رسد | سوکت قطع است، polling فعال | همان حالت اول |
