- **کاربر A** (anbar.arad): تولیدکننده رویداد (ثبت درخواست)
- **کاربر B** (ceo.arad): گیرنده اعلان (مرورگر دوم)

## پیش‌شرط‌ها

سرویس realtime روی 3003/3004 بالا؛ هر دو از گیت‌وی پورت 81 متصل‌اند (سوکت از 127.0.0.1:3000 مستقیم کار **نمی‌کند** — قاعده گیت‌وی).

| # | کنش | رفتار مورد انتظار |

| ۱ | kill پروسه realtime | چیپ B «آفلاین»؛ polling هر ۳۰s ادامه می‌دهد؛ اعلان‌های جدید دیرهنگام ولی از دست نمی‌روند |

| ۳ | رویداد جدید | مجدداً تحویل زنده |

## شاخه‌های خطا و مرزی

| حالت | رفتار |
|---|---|
| بلیت منقضی (>60s) بین GET ticket و register | register رد + reconnect چرخه بلیت تازه |
| دو تب از یک کاربر | هر دو اتاق user:<id>؛ هر دو toast — idempotent روی badge با refetch |
| emit با کلید داخلی غلط | 401 سکوت‌آمیز؛ notify همچنان در DB (منبع حقیقت) |
| سکون شبکه طولانی (بیشتر از ping) | socket.io پینگ/پنگ 60/25s؛ بازگشت = sync از polling |
| کاربرِ فقط‌یک‌بار در روز | هیچ اعلانی حذف نمی‌شود؛ سقف نمایش پاپ‌آور ۲۰ مورد اخیر (بقیه در API) |

## معیار پذیرش

- [ ] تأخیر end-to-end رویداد→toast < ۲s در حالت سوکت سالم.
- [ ] تحویل at-least-once: با سوکت مرده، اعلان با polling حداکثر ۳۰s دیرتر دیده می‌شود.
- [ ] هیچ مسیری باعث «اعلان DB ثبت شد ولی هرگز دیده نشد» نمی‌شود.
- [ ] تست مرورگر فقط از پورت 81 (خطای Transport unknown روی مسیرهای دیگر شناخته‌شده).
- [ ] بعد از restart سرویس، کلاینت بدون تعامل انسانی به بلادرنگ برمی‌گردد.

## نکات پیاده‌سازی مرجع

- بلیت: HMAC-SHA256، ttl 60s، timingSafeEqual — `core/notifications/realtime.ts` + `mini-services/realtime/index.ts`.
- قیف واحد: `notify()` — هر ماژول مستقیماً سوکت صدا نمی‌زند.
- polling مستقل از rtVersion تا هم‌ترازی نهایی.
